# MAD MAX BOT — мониторинг аварий связи

Бот получает сообщения через официальный MAX Bot API, ищет сообщения о проблемах
на объектах связи и перебоях услуг, сохраняет их в SQLite и отправляет оповещения.
Веб-интерфейс, две ленты, статистика, редактор словарей и проверка текста сохранены.
Анализируется текст постов и пересылок; цитата в обычном ответе не считается новой аварией.
Chrome, Selenium, HTML-парсинг лент, Qt и зависимости для Excel удалены.

## Условия доступа MAX

Нужен токен официального бота и доступ API к исходным чатам/каналам. Для событий
`/updates` и Webhook MAX требует права администратора. Доступ к чтению `/messages`
проверяется независимо: если API возвращает посты, программа может опрашивать их
напрямую. Это проверено на текущих двух источниках; доступность других каналов
зависит от разрешений MAX. Подписка вашего аккаунта не определяет права токена бота.

Документация MAX:
[события](https://dev.max.ru/docs-api/methods/GET/updates),
[отправка](https://dev.max.ru/docs-api/methods/POST/messages),
[Webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions).
Используется `https://platform-api2.max.ru`, токен передаётся в заголовке Authorization.
Проверка TLS включена. Если для соединения нужен дополнительный доверенный сертификат,
задайте `SSL_CERT_FILE` с путём к PEM-набору доверенных CA, включая требуемую цепочку.

## Запуск через Docker Compose

Нужен запущенный Docker Engine (на Windows — Docker Desktop в режиме Linux containers).
В корне проекта уже есть `Dockerfile`, `compose.yaml` и шаблон `.env.example`.

Если `.env` ещё нет, создайте его:

```powershell
cd D:\PROJECTS\MAX_BOT
Copy-Item .env.example .env
```

Если `.env` уже существует, сохраните его и добавьте недостающие параметры вручную.
Откройте `.env` и впишите токен после знака `=`:

```dotenv
MAX_BOT_TOKEN=ваш_реальный_токен
MAX_WEB_USER=admin
MAX_WEB_PASSWORD=длинный_уникальный_пароль
MAX_RECEIVE_MODE=polling
MAX_AUTO_START=true
MAX_WEB_PORT=8000
```

При первом запуске проверьте исходные файлы `channels.txt`, `recipients.txt`,
`keywords.json` и `config.ini`: их содержимое будет импортировано в SQLite. Затем запустите:

```powershell
docker compose up -d --build
docker compose logs -f --tail=100 bot
```

Откройте [панель управления](http://127.0.0.1:8000) и войдите с указанными логином и паролем. Мониторинг стартует автоматически,
в том числе после перезапуска контейнера. Для ручного запуска кнопкой **Старт** задайте
`MAX_AUTO_START=false`. Параметр автозапуска работает и при обычном запуске приложения.
Healthcheck проверяет доступность панели и базы; ошибку токена или мониторинга смотрите
в статусе панели и журнале. Одновременно с контейнером не запускайте EXE/CLI с тем же
токеном и базой данных.

Папки `data/` и `output/`, а также прежние файлы настроек подключены из папки проекта.
Настройки панели сохраняются в `data/settings.sqlite`; файлы читаются только при первом
создании базы. Пересборка и удаление контейнера не удаляют базу. Пустой `.env` не позволит
запустить Compose: токен и данные для входа обязательны.
`.env` не попадает в Git или контекст сборки образа.

Посещения панели и успешные/неуспешные попытки входа записываются в `data/access.jsonl`
с временем UTC и IP клиента. Пароли в журнал не записываются. Сессия действует 12 часов;
перезапуск процесса завершает все сеансы. При доступе через reverse proxy настройте
передачу реального IP и доверенные прокси Uvicorn; заголовкам от произвольных клиентов
доверять нельзя. Для удалённого доступа используйте HTTPS.

```powershell
docker compose ps
docker compose down
# Применить изменения .env:
docker compose up -d --force-recreate
```

После изменения исходников используйте `docker compose up -d --build`.
Для другого порта задайте, например, `MAX_WEB_PORT=8080`. Порт привязан к localhost.

Для серверного режима задайте `MAX_RECEIVE_MODE=webhook` и `MAX_WEBHOOK_SECRET`,
настройте HTTPS reverse proxy на `/webhook` по инструкции ниже, затем зарегистрируйте URL:

```powershell
docker compose exec bot python main.py --register-webhook https://your-domain.example/webhook
```

Команда использует переменные уже запущенного контейнера. Секреты в образ не встраиваются.
Образ автоматически добавляет CA Минцифры к стандартному набору certifi и задаёт
`SSL_CERT_FILE=/opt/max-ca-bundle.pem`. Публичные сертификаты загружаются при сборке
с официального домена Госуслуг, проверяются по закреплённым SHA-256 и разбираются OpenSSL.
Если их содержимое изменится, сборка остановится до проверки и обновления контрольных сумм.

### Диагностика подключения MAX в Docker

```powershell
docker compose exec bot python diagnose_api.py
docker compose logs --tail=40 bot
```

Диагностика не читает и не отправляет токен. Ответ `HTTP 401` на запрос без токена
означает, что DNS, соединение и TLS работают. Настоящий `HTTP 503` означает ответ
сервера/шлюза. Ошибки DNS, таймауты, прокси и TLS отображаются отдельно в статусе
мониторинга; они больше не маскируются под HTTP 503.

Если диагностика показывает ошибку проверки TLS-сертификата, подготовьте полный
доверенный PEM-набор CA в `certs/ca-bundle.pem`: обычные корневые сертификаты и
необходимые дополнительные сертификаты из доверенного источника. В частности,
[документация MAX](https://dev.max.ru/docs-api) указывает на необходимость доверия
сертификату Минцифры. Windows и Linux-контейнер используют разные хранилища доверия.
Для подключения готового набора предусмотрен дополнительный Compose-файл:

```powershell
docker compose -f compose.yaml -f compose.ca.yaml up -d --build
docker compose -f compose.yaml -f compose.ca.yaml exec bot python diagnose_api.py
```

При использовании этого набора запускайте последующие команды с обоими `-f`.
PEM-файл остаётся на компьютере и подключается только для чтения; приватные ключи
не нужны. Проверка сертификатов остаётся включённой. Если показан настоящий HTTP 503,
добавление CA его не исправит: проверьте доступность сервиса, прокси и сеть сервера.

В старых образах отсутствие CA маскировалось под HTTP 503. Для обновления достаточно
`docker compose up -d --build`; при стандартном подключении к MAX дополнительный
`compose.ca.yaml` не нужен. Он предназначен для собственного набора CA, например,
при наличии корпоративного HTTPS-прокси.

## Локальный запуск

Python 3.12+ и uv:

```powershell
uv sync
uv run python main.py
```

При локальном запуске приложение читает `MAX_BOT_TOKEN`, `MAX_RECEIVE_MODE`,
`MAX_WEBHOOK_SECRET`, `MAX_WEB_USER`, `MAX_WEB_PASSWORD` и `MAX_AUTO_START` из `.env` в папке проекта. Если `.env` ещё нет,
скопируйте `.env.example` и впишите токен. Значения, заданные в окружении процесса,
имеют приоритет над `.env`.

Для локального Python или EXE при ошибке проверки TLS создайте полный CA-набор из
стандартных корневых сертификатов и сертификатов Минцифры:

```powershell
New-Item -ItemType Directory -Path certs -Force | Out-Null
uv run python ca_bundle.py certs/ca-bundle.pem
uv run python diagnose_api.py
```

Скрипт скачивает сертификаты с официального домена, проверяет закреплённые SHA-256
и сохраняет набор в `certs/ca-bundle.pem`. Локальное приложение использует этот файл
автоматически, если `SSL_CERT_FILE` или `SSL_CERT_DIR` не заданы. Диагностика не
передаёт токен; `HTTP 401` означает, что TLS работает. Для EXE разместите набор
в папке `certs` рядом с исполняемым файлом.

Откройте [интерфейс](http://127.0.0.1:8000), проверьте источники и адресатов в настройках,
нажмите **Старт**, если `MAX_AUTO_START` выключен. Токен не возвращается в интерфейс.
После изменения `.env` или переменных окружения перезапустите процесс.

`channels.txt` используется только для первого импорта: по одному числовому `chat_id` на строку. Поддерживаются прежние ссылки
`https://web.max.ru/-123456789`, если последний компонент — числовой ID.
В веб-настройках можно вставить публичную ссылку `https://max.ru/имя_канала`:
приложение один раз читает публичную страницу MAX, извлекает `channelId` и сохраняет
числовой `chat_id` в SQLite. Если формат страницы изменится, сохранение сообщит об ошибке.
Пригласительные ссылки не содержат пригодного ID. Если публичная ссылка не разрешается,
получите ID из события `bot_added` через `/updates` или Webhook согласно
[документации MAX](https://dev.max.ru/docs-api/use-cases/getting-chat-id).

`recipients.txt` используется для первого импорта:

```text
# Группа или канал, в котором бот имеет право писать
chat:-123456789
# Пользователь, которому бот может отправить сообщение
user:123456789
```

Обычный числовой ID трактуется как **chat_id**. Для пользователя указывайте `user:`.
Прежнее «Избранное» (`0`) не поддерживается API, поэтому удалено из шаблона адресатов.
Пустой список адресатов оставляет мониторинг и сохранение без рассылки.
Источник и чат рассылки должны различаться, собственные сообщения бота пропускаются.

Long Polling предназначен MAX для разработки и тестирования и имеет ограниченное
хранение событий. При первом подключении источника загружаются до 100 последних постов
через `/messages`: они отображаются и фильтруются, но не рассылаются. Затем программа
использует события либо повторный опрос `/messages`, если доступ к событиям не подтверждён.
Для явного опроса постов задайте `MAX_RECEIVE_MODE=messages`; в этом режиме `/updates`
не вызывается. Следующие снимки дедуплицируются, новые посты могут рассылаться.
История старше первого снимка автоматически не импортируется. Указатели событий и
истории сохраняются в SQLite отдельно для каждого бота/источника. После простоя
опрос истории запрашивает страницы до сохранённого времени. Не запускайте несколько
worker с одной базой и токеном.

```powershell
uv run python main.py --cli
uv run python main.py --cli --once --no-send
uv run python main.py --cli --interval 10
uv run python main.py --host 127.0.0.1 --port 8000
```

`--once` обрабатывает один пакет/снимок API и сохранённую очередь. `--interval` задаёт
интервал опроса `/messages` и базовую паузу при ошибках API. Обычный polling ждёт события до 20 секунд. Остановка может
занять до 30 секунд из-за текущего HTTP-запроса.

## Webhook для сервера

MAX рекомендует Webhook для production. Подготовьте публичный HTTPS-адрес на порту 443
с доверенным сертификатом и проксируйте **только `/webhook`** на локальное приложение.
Панель управления защищена собственным входом. Для публикации панели используйте HTTPS.

```powershell
$env:MAX_BOT_TOKEN = 'токен-вашего-бота'
$env:MAX_RECEIVE_MODE = 'webhook'
$env:MAX_WEBHOOK_SECRET = 'случайный_секрет_из_латиницы_цифр_и_дефисов'
uv run python main.py
```

В другом терминале с теми же переменными зарегистрируйте адрес:

```powershell
uv run python main.py --register-webhook https://your-domain.example/webhook
```

Это явная команда регистрации, запуск приложения сам подписку не меняет. Секрет должен
содержать 5–256 символов `A-Z`, `a-z`, `0-9`, `_`, `-`. Настройте автозапуск процесса
с теми же переменными и нажмите **Старт** для обработки очереди в веб-интерфейсе.
Для автоматической обработки без панели можно запускать отдельный процесс `--cli`
с той же базой; запускайте только один worker.

Приёмник проверяет `X-Max-Bot-Api-Secret`, ограничивает размер тела 1 МБ и отвечает
200 только после записи события в SQLite. Остановка worker не отключает приёмник:
события ждут в очереди до следующего запуска. После регистрации Webhook не используйте
polling с тем же ботом; для возврата на polling сначала удалите подписку через API MAX.

## Поиск проблем связи

Если мониторинг запущен, а лента пуста, проверьте источники:

```powershell
docker compose exec bot python diagnose_sources.py
```

Команда проверяет бота, конфликт polling/Webhook, членство и права в каждом канале,
а также доступность чтения последних сообщений. Она не отправляет сообщения, не
потребляет очередь `/updates` и не выводит токен или тексты постов. HTTP 403 на
`/chats/<id>/members/me` означает, что доступ к событиям не подтверждён; при этом
нужно отдельно проверить `/messages`. Если и чтение постов запрещено, добавьте бота
администратором с правом `read_all_messages` либо укажите доступный ему источник.

При запуске worker проверяет возможности API и конфликт polling/Webhook.
Статус показывает число обработанных событий, новых записей, повторов и событий
из источников вне настроенного списка, а также число источников, опрашиваемых через `/messages`.
В правой колонке появляются все прочитанные сообщения, даже если фильтр не нашёл аварию.
Первый снимок, повтор того же поста через события и перезапуск не рассылают историю.

Пять редактируемых групп сохраняются в `data/settings.sqlite`. При первом запуске они
импортируются из `keywords.json` (если его нет, прежний `keywords.txt` заполняет только
группу 1):

| Группа | Назначение |
|---|---|
| 1. Тематика | Операторы, ВОЛС, базовые станции, узлы связи, ЦОД, телефония, интернет |
| 2. Негатив | Аварии, повреждения, обрывы, отключения, отсутствие услуг |
| 3. Статус | «Не работает», проблемы звонков, плановые работы, ограничения |
| 4. Топоним | Географическая метка; сама по себе не делает сообщение аварией |
| 5. Восстановление | Подтверждённое устранение и восстановление |

Нужны тематика **и** сигнал из групп 2, 3 или 5. Если тематический список намеренно пуст,
используется поиск по аварийным сигналам без обязательного тематического слова.
Порог числа совпадений применяется дополнительно. Пунктуация как ключевое слово
игнорируется. Регистр и `ё/е` не важны, фразы учитывают распространённые окончания,
варианты задаются через `|`.

Примеры:

| Текст | Результат |
|---|---|
| «МТС открыл офис в Москве» | Не проходит |
| «ВОЛС повреждена, у жителей нет интернета» | Критическое |
| «Мобильный интернет не работает» | Активное |
| «Сбой Мегафона устранён, связь восстановлена» | Нормальное |
| «Сбой ещё не устранён, связь МТС не восстановлена» | Критическое |
| «Плановые работы: отключение интернета» | Активное + плановые работы |

Частичное восстановление и продолжающиеся перебои не снимают тревогу. Отрицания
«без сбоев» и «сбоев не зафиксировано» исключаются. Обещание восстановить связь
не считается завершённым восстановлением. Все сообщения остаются в правой ленте,
совпадения — в левой. Можно слать только критические.

В правой ленте показаны локальные дата и время публикации. Поиск по тексту, источник,
статус и период отбирают записи из всей сохранённой базы; порядок можно переключить
между новыми и старыми. За один запрос отображается до 160 сообщений.

Перед рассылкой действует дополнительная проверка: в одном предложении должны быть
признаки фактического действующего сбоя связи. Плановые работы, сообщения о риске или
возможном повреждении, предложения о будущих отключениях и уже устранённые сбои
остаются в ленте совпадений с пометкой «без рассылки». Эта проверка применяется и к
ожидающим сообщениям в очереди после пересчёта архива при запуске или сохранении
настроек.

Это объяснимый словарный фильтр, а не семантическая модель: сложные отрицания, цитаты,
несколько событий в одном посте и неоднозначные названия требуют проверки оператором.
Словарь ориентирован на российские сети, география не является жёстким ограничением:
локальное сообщение часто не содержит название региона. OCR, расшифровка аудио,
выявление реальной аварии вне сообщений и объединение постов в единый инцидент не реализованы.

Сохранение настроек пересчитывает архив, включая снятие прежних ложных совпадений.
Архив при этом не рассылается. Новые события используют настройки со следующей итерации.

## Доставка и хранение

`data/messages.sqlite` совместима с прежней таблицей сообщений; новые таблицы добавляются
автоматически. Удалять базу для обновления не нужно. Перед переносом сделайте резервную
копию при остановленном приложении.

- `messages`: архив и результат фильтрации; API-сообщения различаются по chat_id + mid.
  Для пересылки без собственного body используется исходный mid и время пересылки.
- `inbox`: постоянная очередь входящих событий; marker меняется в одной транзакции с записью пакета.
- `outbox`: очередь оповещений, подтверждение отдельно для каждого адресата.
- `api_state`: сохранённые указатели получения событий.
- `output/messages.jsonl`, `output/matches.jsonl`, `output/monitor.log`: экспорт и журнал.

Временные ошибки и HTTP 429 приводят к повтору с задержкой. HTTP 401/403 останавливают
worker с ошибкой, чтобы можно было исправить токен или права. Подтверждённые получатели
не получают повторов при штатном повторе очереди. При обрыве соединения **после приёма
сообщения MAX, но до получения ответа**, либо аварии до записи подтверждения в SQLite,
возможна повторная отправка: гарантия exactly-once на стороне MAX не предполагается.
Экспорт JSONL не является транзакционной очередью; SQLite — основной источник данных.

Отправка отключённым или удалённым адресатам приостанавливается. Уже накопленные
оповещения могут уйти при повторном включении отправки/возврате адресата. Таблицы очередей
сохраняются для восстановления и аудита, автоматическая очистка не выполняется.

## Проверки и сборка

```powershell
uv sync --group dev
uv run pytest
uv run pyinstaller mad_max_bot.spec
```

Тесты проверяют фильтрацию на русскоязычных примерах, контракт HTTP, Webhook, защиту
токена, дедупликацию, восстановление очереди и повтор частичной рассылки. Настоящий токен
для тестов не нужен. Сборка создаёт `dist/MAD_MAX_BOT/MAD_MAX_BOT.exe` с веб-интерфейсом
и шаблонами настроек. Для EXE поместите `.env` рядом с `MAD_MAX_BOT.exe` либо задайте
переменные окружения перед запуском. Файл `.env` не включается в сборку.

Основные модули: `max_api.py` — HTTP-клиент, `parser.py` — данные API,
`monitor.py` — обработка событий и доставка, `matcher.py` — фильтр,
`store.py` — SQLite, `server.py` — панель и Webhook, `main.py` — запуск.

Локальное API панели: `GET /api/feed`, `GET/PUT /api/settings`,
`POST /api/preview`, `POST /api/start`, `POST /api/stop`.
